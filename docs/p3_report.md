# P3(정확해법) 결과 보고

작성일: 2026-11-18 · 대상: `docs/design.md` 6장의 P3 · 결론: **게이트 문구는 충족, 단 합성 SP 세트(`sp`)의 해 품질과 증명은 미흡.**
P4는 시작하지 않았다(사용자 승인 후). 커밋도 하지 않았다(기준 커밋 `91c9602` 뒤 변경은 작업 트리에만 있음).

## 1. 범위와 순서

설계서의 P3는 "B&B, reduced cost fixing, reliability·Ryan–Foster 분기, diving, RINS, feasibility pump"이고 게이트는
"scp4x/6x와 작은 SPP를 최적 증명, 모든 SPP에서 실행 가능해 확보"다.

고른 순서와 이유:

1. **이어 푸는 LP(`LpSolver`)** — B&B의 모든 것이 여기에 달려 있어 가장 먼저 했다. 경계만 바뀌면 기저가 dual feasible로 남으므로
   dual simplex로 이어 푼다. 기저 저장·복원, dual 목적값 cutoff, 반복 한도를 넣었다.
2. **SC 최적 증명**(LP 하한 B&B + reduced cost fixing) — 사용자 결정대로 먼저 했다. P1이 이미 좋은 해를 주므로 하한만 올리면
   증명이 되고, 효과를 P1과 바로 비교할 수 있다.
3. **LP를 P1에 연결** — 루트 LP 값을 하한으로, 루트 reduced cost를 열 고정에 쓴다. LP dual을 P1의 Lagrangian 승수로도 넘겨
   봤으나 greedy 해 품질이 나빠져(2000열 DMS) 뺐다. 지금은 **하한과 열 고정에만** 쓴다.
4. **분할·혼합 문제 경로**(`solve_bin`) — P1이 다루지 못하는 모델(= 행, 부가 제약)을 같은 B&B로 푼다. 첫 해를 찾는 휴리스틱이
   여기서 필요해져 diving, exact cover 탐색, feasibility pump를 붙였다.
5. **primal simplex 보강은 미뤘다** — B&B는 dual simplex만 쓴다(경계 변경 뒤 재최적화). 필요한 곳이 없었다.

구현하지 않은 것: **RINS, local branching**(설계서 P3 목록에 있음). 5.3절에 영향과 함께 적었다.

## 2. 구현한 것

| 구성 | 파일 | 내용 |
|---|---|---|
| 이어 푸는 LP | `include/scsp/lp.hpp`, `src/core/lp.cpp` (`LpSolver`) | 경계 변경 → dual simplex 재최적화, 기저 저장·복원, cutoff, 반복 한도, 정체 시 비용 섭동 |
| B&B | `include/scsp/bnb.hpp`, `src/core/bnb.cpp` | 최선 하한 노드 선택 + 내려가기, 1 쪽 가지 먼저, 정수 비용이면 하한 올림 |
| 열 고정 | `bnb.cpp` | 루트 reduced cost로 열을 걸러 트리에 넘김. 해가 나아질 때마다 트리 안에서도 다시 고정 |
| 분기 | `bnb.cpp` | reliability branching(pseudocost + strong branching), 순수 분할 문제는 Ryan–Foster |
| 첫 해 찾기 | `bnb.cpp` | LP 내려가기 1회 → exact cover 탐색 → (3000노드 또는 시간 10% 뒤) feasibility pump → 무작위 내려가기 반복. LP 해 greedy 반올림 |
| SC 연결 | `src/core/sc_solver.cpp` | 3스레드 이상이면 한 스레드가 루트 LP와 트리를 전담, 나머지는 P1 휴리스틱. 2스레드 이하는 마지막 스레드가 둘을 번갈아 함 |
| 일반 0-1 경로 | `include/scsp/bin_solver.hpp`, `src/core/bin_solver.cpp` | 덮기가 아닌 모델. 트리 1스레드 |
| Python | `python/scsp/solve.py`, `python/scsp/lp.py` | `scsp.solve`가 모델에 따라 `sc` 또는 `bin` 경로로 보냄(`stats["path"]`). `scsp.LpSolver` |

`scsp.solve`는 이제 어떤 0-1 모델이든 받는다(P2까지는 덮기 문제만, 나머지는 `NotImplementedError`). `bnb=False`를 주면 P1 동작 그대로다.

검증: 테스트 131개 통과(P3에서 `tests/test_bnb.py`, `tests/test_lpsolver.py` 추가), `-Wall -Wextra -Wpedantic -Werror` 빌드 통과.
무작위 모델 300개(혼합 행, 분할, 덮기 + 부가 제약)를 1·4스레드로 풀어 HiGHS MIP와 대조했고 최적값·불가능 판정이 전부 일치했다.

## 3. LP 인터페이스 결정 (사용자 결정 "1. (나) 2. (가) 3. (가)")

**1. (나) Python 노출** — `scsp.LpSolver`.

```python
lp = scsp.LpSolver(model)            # LP 완화(0 ≤ x ≤ 1). LpSolver.from_arrays(...)는 일반 LP
lp.solve()                           # "optimal" | "infeasible" | "unbounded" | "limit" | "failed" | "cutoff"
lp.obj, lp.x, lp.red_cost, lp.row_dual()
lp.set_col_bounds(j, 1.0, 1.0)       # 다음 solve()는 직전 기저에서 이어 풂
basis = lp.get_basis(); lp.set_basis(basis)
lp.set_cutoff(z)                     # dual 목적값이 z를 넘으면 "cutoff"로 멈춤. None이면 해제
```

테스트 11개(`tests/test_lpsolver.py`): 첫 풀이가 `solve_lp`와 같은지, 경계를 바꾼 뒤 값이 새로 푼 것과 같은지(무작위 고정 반복),
이어 풀기가 처음부터 풀기보다 반복이 적은지, 기저 저장·복원, cutoff와 반복 한도, 잘못된 입력.

**2. (가) 컷은 선언만** — `add_rows` / `remove_rows`를 C++에 선언했다. P4 전까지 C++에서는 `std::logic_error`를 던지고,
**Python에서는 메서드를 노출하되 호출하면 `NotImplementedError`를 낸다.** 숨기지 않은 이유: 인터페이스 모양(행 단위 CSR + 행 하한·상한,
`remove_rows(first_row)`는 그 행부터 끝까지 삭제)을 지금 고정해 두면 P4에서 시그니처를 바꾸지 않아도 된다.

**3. (가) 열이 많은 문제** — 루트는 `solve_lp`(열이 많으면 sifting)로 풀고, reduced cost로 걸러 남은 열만 트리의 LP에 싣는다.

- 해(incumbent)가 있을 때: `올림(루트 LP값 + max(d_j, 0)) ≤ 해 − 1`(정수 비용) 인 열만 남긴다. 버린 열은 더 좋은 해에 들어갈 수 없으므로 증명이 유효하다.
- 해가 없을 때(분할 문제 초반): reduced cost가 작은 순으로 `max(4m, 2000)`개만 실은 **제한 트리**로 첫 해를 찾는다. 해를 못 찾고 끝나면 4배로 넓힌다.
  해를 찾으면 그 트리를 마친 뒤 위 기준으로 다시 걸러 정확한 트리로 넘어간다. 제한 트리에서는 하한을 올리지 않는다.

인스턴스별 남은 열 수와 루트 gap은 4.4절(요약)과 부록(153개 전부)에 있다.

## 4. 게이트 측정

조건: 153개 인스턴스(SC 90, SPP 63), 30초, 4스레드, 실행마다 별도 프로세스로 하나씩 순서대로. seed는 기본 1·2·3이고,
잡음이 큰 세트(dms, scpnrg, scpnrh, rail)는 P3·P1 모두 seed 4·5를 더해 5개로 쟀다. 5/10초 값은 30초 실행의 trace에서 읽었다.
P3 실행 519개 전부 해를 냈고 독립 검증(`verified`)을 통과했다. 하한이 알려진 최적값을 넘거나 "optimal" 값이 최적값과 다른 실행은 없다.

- P1 기준(`scsp-p1`): seed 1~3은 P1 당시 실행, seed 4·5는 지금 코드에 `bnb=False`를 준 실행이다.
- HiGHS 1.16.0·Gurobi 13.0.2는 P0의 60초 실행을 그대로 쓴다. "30초 안 증명"은 실행 시간으로 셌다. Gurobi는 크기 제한 안의 71개만 있다.
- 측정 뒤에 `LpSolver` Python 바인딩을 빌드했다. 추가한 것은 접근 함수와 바인딩뿐이고 탐색 코드는 그대로라 측정값에는 영향이 없다.

- `benchmarks/bks.csv`와 `summary_*.csv`를 새 실행으로 다시 만들었다. BKS 값이 바뀐 것은 두 개다(더 좋은 해를 찾음):
  dms_K300_n20000_s1 3194.452 → 3194.388, dms_K500_n30000_s1 3249.646 → 3249.380. 표시(flag)된 불일치는 0건이다.

### 4.4 남은 열 수와 루트 gap (결정 3)

- **루트 gap** = (BKS − 루트 LP값) / BKS.
- **남는 열(BKS 기준)** = BKS를 해로 알고 있을 때 3장의 기준을 통과하는 열 수. 원 문제의 LP로 계산했다 — 걸러낼 수 있는 한계치다.
- **트리에 실은 열(실행)** = 실제 실행에서 마지막 트리의 LP에 실린 열 수. SC 경로는 presolve 뒤 문제 기준이고 그때의 해가 BKS보다 나쁠 수 있어
  한계치와 조금 다르다. 일반 경로(SPP)는 제한 트리의 크기(`max(4m, 2000)`)가 그대로 찍힌 경우가 많다 — 트리 안에서 고정한 열은 빼지 않고
  경계만 0으로 묶기 때문이다. 실제로 살아 있는 열은 "BKS 기준" 쪽에 가깝다.

## 5. 한계와 알려 둘 점

### 5.1 스레드 배치

4스레드에서 휴리스틱 3 + 트리 1로 나눈다. 시도한 대안: (a) LP dual을 휴리스틱 승수로 쓰기, (b) 한 스레드가 휴리스틱과 트리를 번갈아 하기.
둘 다 2000열 DMS에서 해 품질이나 증명 속도가 나빠져 버렸다. 지금 배치는 작은·중간 문제의 증명에는 좋지만 4.3절처럼 큰 문제(열 2만 이상, scpnrh)에서
휴리스틱 품질을 깎는다. 트리가 가망 없을 때 스레드를 돌려주는 규칙은 넣지 않았다.

### 5.2 DMS 증명

2000열 K200~300은 20~25초가 걸리고(Gurobi 0.5~0.8초, HiGHS 7~9초), K500과 1만 열 이상은 30초에 증명하지 못한다. 30초 뒤 남는 gap은
dms_K500_n2000 0.36%, dms_K200_n10000 0.61%, 큰 것은 1.2~2.4%다. strong branching 호출이 노드 수와 비슷할 만큼 많다(dms_K200_n2000: 9477노드, 9084회).

### 5.3 구현하지 않았거나 약한 것

- **RINS, local branching 미구현.** 합성 `sp`에서 첫 해 이후 개선이 없는 직접 원인이다.
- **feasibility pump는 구현했지만 효과가 없었다.** 시험한 분할 문제에서 해를 찾지 못했다. 첫 해는 거의 exact cover 탐색과 내려가기가 찾는다.
- **일반 경로는 트리 1스레드**이고 SP 전용 presolve가 없다. 4스레드를 줘도 SPP에서는 1스레드만 쓴다.
- **노드별 reduced cost fixing 없음.** 루트 reduced cost로만 고정한다.
- **컷 없음**(P4).
- 설계서 5.3절의 "최적 증명용 600초 실행"은 하지 않았다. 게이트는 30초 실행으로 판정했다.
- primal simplex는 P2 상태 그대로다.
- Linux 빌드는 확인하지 않았다(사용자 결정: Mac에서만). `scripts/linux_build.sh`(docker)는 소스 목록이 CMake에서 오므로 고칠 것이 없었고,
  docker 없이 쓰는 `scripts/linux_native_build.sh`를 새로 써 두었다(실행하지 않음).

### 5.4 P3에서 찾아 고친 문제

- dual simplex가 퇴화한 LP에서 오래 제자리걸음 → 2m+200회 뒤 비용 섭동을 한 번 더 건다. 이걸로 sppkl02에서 해를 찾고 rail582를 약 4초에 증명하게 됐다.
- 분할 문제에서 내려가기·feasibility pump만으로는 해를 못 찾는 경우(sp_m400, sp_m300_n10000, sppkl02) → exact cover 탐색, 제한 트리 넓히기, 시간 기준 휴리스틱 전환 추가.
- `LpSolver.solve(max_iter)` 바인딩이 cutoff 자리에 NaN을 넘기던 것을 빌드 전에 발견해 고쳤다.

## 8. P4 전에 정할 것

1. **합성 `sp`의 약점을 어디서 메울지.** RINS·local branching(P3 범위의 미구현분)을 먼저 넣을지, P4의 clique 컷으로 넘어갈지.
   내 의견: 컷이 하한과 해 품질 양쪽에 듣고 DMS 증명에도 필요하므로 P4를 먼저 하고, RINS는 P4 안에서 붙인다.
2. **큰 문제에서 트리 스레드 처리.** 루트 gap과 크기를 보고 트리 스레드를 휴리스틱으로 돌려주는 규칙을 P4 초반에 넣을지, P5(병렬·튜닝)로 미룰지.
   P1 대비 회귀(6만 열 DMS에서 5초 +0.9~1.2%)를 그대로 둘지의 문제다.
3. **DMS용 컷의 종류.** DMS는 덮기(≥) 문제라 clique 컷이 직접 맞지 않는다. 설계서 P4의 odd-hole·zero-half 중 무엇부터 할지는 루트 gap 감소를 재 보고 정하는 것이 좋다.
