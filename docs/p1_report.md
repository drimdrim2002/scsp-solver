## 2. 통과 기준 측정

| 읽는 방법 | 5초 | 10초 | 30초 | 판정 |
|---|---|---|---|---|
| 엄격한 우위(더 좋음) / 전체 90개 | 17.8% | 13.3% | 8.9% | **미충족** |
| 나쁘지 않음(승 + 무) / 전체 90개 | 96.7% | 95.6% | 93.3% | 충족 |
| 더 좋음 / HiGHS가 그 시점에 BKS에 못 미친 인스턴스 | 16 / 20 = 80% | 12 / 15 = 80% | 8 / 11 = 73% | 5·10초 충족, 30초 미충족 |

### 최적 증명 (P1의 기준은 아님)

270개 실행 중 147개(49개 인스턴스)를 30초 안에 최적으로 증명했다. 같은 90개에서 HiGHS는 30초 안에 204개 실행을 증명한다.

- scp4·5·6·e와 rail516은 0.1초 안에 증명한다(HiGHS는 0.01~2.3초, rail516은 4.5~7.4초).
- scpa는 전부(평균 1.2초), scpb·scpc는 15개 중 9개, scpd는 3개만 증명했다. HiGHS는 이 네 세트를 모두 6.1초 안에 증명한다.
- scpnre·scpnrf, rail507·rail582, 번들 2000개 이상 DMS 대부분은 증명하지 못했다. 30초 시점의 하한 격차는 DMS 평균 1.1%,
  scpnrg 10.5%, scpnrh 23.7%다(하한은 Lagrangian 한계라 LP 한계를 넘지 못한다).
- LP와 branch-and-cut이 없는 P1의 탐색은 Lagrangian 한계만 쓰는 DFS라서 증명력이 약하다. 설계서대로 P2~P3의 일이다.

## 4. 구현한 것

| 부분 | 파일 | 내용 |
|---|---|---|
| 모델 | `include/scsp/problem.hpp`, `src/core/problem.cpp` | 커버 행 CSR/CSC + 부가 제약(`Σ a x ≤ b`, a ≥ 0), 비용 ≥ 0 검사 |
| presolve | `src/core/presolve.cpp` | 부가 제약에 안 들어가는 열 제거, 단일 열 행 고정, 빈 열, 비용 검사(순수 SC), 열 지배(부가 계수 포함), 행 지배. 최대 6회 반복, 원래 열로 되돌리는 맵 |
| Lagrangian 엔진 | `src/core/sc_solver.cpp` | 행 승수 u와 부가 제약 승수 v의 subgradient(정체 시 스텝 절반), core 문제와 pricing(core 한계를 전체 열로 확인), Lagrangian 비용 greedy, 열 고정과 refinement(3단계 반복), reduced cost 고정 |
| local search | 같은 파일 | 열 하나 추가 후 불필요해진 열 제거, 부가 제약 확인 |
| 탐색 | 같은 파일 | 덮이지 않은 행 분기 DFS(남은 문제의 Lagrangian 한계로 가지치기) — 뿌리에서 끝나면 최적 증명. 현재 해 일부를 고정하고 나머지를 DFS로 다시 푸는 LNS |
| 병렬 | 같은 파일 | `std::thread` worker 4개가 최고해·하한 공유. 홀수 worker는 자기 해를 따로 개선 |
| Python | `python/scsp/solve.py` | `scsp.solve(model, time_limit, threads, seed, warm_start, ...)`, 결과를 `Model`로 재검사 |
| DMS 어댑터 | `python/scsp/dms.py` | `solveSP(...)`: `HighsSP.solveSP`와 같은 인자·반환값. 초기해를 warm start로 쓰고 그보다 나쁜 해는 돌려주지 않음 |
| 하네스 | `python/scsp/bench/runners.py`, `compare.py` | `scsp` 설정, 두 설정의 승/무/패 비교 |
| 테스트 | `tests/test_solver.py` | 9개: 전수 탐색과 일치, 옵션 조합, HiGHS와 최적값 일치, warm start 보장, presolve 맵, 지원하지 않는 모델, 불가능 모델, 어댑터 인터페이스 |

- 기법별 출처는 `docs/references.md` 3장에 추가했다(Beasley 1990, Caprara–Fischetti–Toth 1999 등 공개 문헌).
  다른 솔버의 소스는 열지 않았다. HiGHS는 블랙박스로 LP 값만 구해 우리 하한을 점검하는 데 썼다.
- 범위 밖 모델(분할 = 1 행, `≥`·`=` 부가 제약, 음수 비용·계수)은 `NotImplementedError`를 낸다.
- Mac(Apple clang, `-Wall -Wextra -Wpedantic -Werror`) 빌드와 전체 테스트 38개 통과.

## 5. 측정 방법과 확인

- Apple M4, 4스레드, seed 1·2·3, 실행마다 별도 프로세스로 한 번에 하나씩. 총 270개 실행(66분), 오류 0건, 돌려받은 해는 모두 `Model`로 재검사해 통과.
- scsp는 30초 실행 한 번의 trace에서 5/10/30초 값을 읽었다(HiGHS·Gurobi는 P0의 60초 실행 trace). warm start 없음.
- 시간 제한을 따로 준 실행과 비교(`benchmarks/results/validation/scsp_literal.jsonl`, 6개 인스턴스 × 5·10초, seed 1): 12건 중 7건 일치.
  나머지 5건은 0.01~0.09% 차이(따로 실행이 더 좋은 쪽 3건, 나쁜 쪽 1건)와 rail507의 1 차이(175 vs 176)다.
  4스레드 탐색이 실행마다 조금씩 달라지기 때문이며, 같은 seed라도 결과가 완전히 재현되지는 않는다.
- 원자료: `benchmarks/results/runs/scsp.jsonl`, 비교표 `benchmarks/results/p1_vs_highs*.{md,csv}`, `p1_vs_gurobi*`, 로그 `p1_run.log`.

## 6. 한계와 설계서와 달라진 점

- **Linux 빌드 미확인**: P1 코드는 Mac에서만 빌드했다. 표준 헤더와 `std::thread`만 썼지만 확인은 colima를 켜야 한다(승인 필요).
- **DMS 어댑터는 실제 DMS 엔진으로 돌려 보지 않았다.** 합성 입력과 가짜 라이더 객체로 인터페이스와 해의 변환만 시험했다. `myalgorithm.py`와 DMS 폴더는 건드리지 않았다.
- **warm start 조건의 벤치마크는 없다.** 실사용(ALNS 해를 주고 짧게 푸는 경우)의 효과는 아직 재지 않았다.
- **비결정성**: worker들이 최고해를 주고받는 시점이 실행마다 달라 같은 seed로도 값이 달라질 수 있다.
- **scpnrg 약점**: nrg2~nrg5에서 BKS보다 1 큰 값에 머무는 일이 많다(30초 평균 격차 0.33%, HiGHS 0.13%).
- **번들 2000개 DMS**(K200~K500): 최적과 0.002~0.09% 차이가 남는다. Gurobi·HiGHS는 LP 기반으로 금방 최적에 닿는 구간이다.
- `sc_solver.cpp`에 환경 변수 `SCSP_DEBUG_SUB`로 켜는 진단 출력이 남아 있다(기본은 꺼짐).
- `benchmarks/results/baseline_report.md`와 `summary_*.csv`는 이제 scsp 행도 포함한다. scsp는 30초 실행이라 60초 열은 30초 안에 끝난 실행만 센다.
- `python/scsp/bench/bks.py`의 출처 문구를 "baseline runs"에서 "benchmark runs"로 바꿨다(scsp 값도 들어가므로).

## 7. 승인이 필요한 일 (하지 않음)

1. **커밋**: 저장소는 아직 git 저장소가 아니고 커밋도 없다.
2. **Linux 확인**: `colima start` 후 `scripts/linux_build.sh` 실행.
3. **시간 제한별 전체 격자 실행**(5/10/30/60초를 각각, 약 5시간) 여부.
4. 새 패키지 설치·다운로드는 P1에서 하지 않았고 지금 필요한 것도 없다.

## 8. P2 전에 결정할 점

1. **P1 통과 판정**: 2장의 세 해석 중 무엇을 기준으로 할지. 엄격한 우위는 구조적으로 달성할 수 없다.
2. **P1을 더 다듬을지, P2로 갈지**: scpnrg와 번들 2000개 DMS의 남은 차이, 증명력 부족은 LP·branch-and-cut(P2~P3)이 들어오면
   자연히 줄어들 부분이다. DMS 실사용 크기가 큰 쪽(번들 수만 개)이라면 지금 상태로도 HiGHS보다 좋다.
3. **실제 DMS 연결 시험**: DMS 코드에서 `from scsp.dms import solveSP`로 바꿔 한 번 돌려 볼지(DMS 폴더 수정이 필요하므로 사용자 결정).
4. **warm start 비교**를 P1 범위로 추가할지.
5. **결정적 모드**(스레드 간 공유 시점을 고정)를 넣을지 — 대회 제출에서 재현성이 필요한지에 달렸다.

## 9. 사용자 결정 (2026-11-17, 보고 뒤 기록)

- **P1을 더 다듬지 않고 P2로 진행한다**(사용자: "p2로 넘어갈께요"). 통과 기준의 해석은 따로 고르지 않았다.
- 판정 기록: 원래 기준(더 좋음 ≥ 80%)은 **미충족**. 개선 여지가 있던 인스턴스 기준으로는 5초 80%, 10초 80%, 30초 73%.
- 약점 세 가지(scpnrg의 +1, 번들 2000개 DMS의 0.002~0.09% 차이, 최적 증명력)는 P2~P3 과제로 넘긴다.
- 7·8장의 나머지 항목(커밋, colima Linux 확인, 실제 DMS 연결 시험, warm start 비교, 결정적 모드)은 답이 없어 하지 않는다.
