# P2(LP 엔진) 결과 보고

작성일: 2026-11-17 · 대상: `docs/design.md` 6장의 P2 · 결론: **게이트 충족.** P3는 시작하지 않았다(사용자 승인 후).

## 1. 범위

설계서 6장의 P2는 "LP 엔진: dual/primal simplex, 희소 LU, sifting"이고 게이트는 "전 인스턴스에서 HiGHS LP와 목적값
상대오차 ≤ 1e-6, 속도는 HiGHS LP의 몇 배 이내인지 보고"다. 이 범위대로 구현했다. 분할(= 1) 문제의 정수해 탐색
(diving, feasibility pump, B&B)은 설계서상 P3이라 손대지 않았다. LP 엔진은 그 SP 경로의 바탕이다.

## 2. 게이트 측정

조건: 156개 인스턴스 전부, 각 모델의 LP 완화(0 ≤ x ≤ 1), 솔버마다 1스레드, 인스턴스마다 별도 프로세스로 한 번씩 순서대로.
HiGHS 1.16.0은 기본 설정(presolve 켬)이 기준이고 presolve를 끈 실행도 함께 쟀다. 시간은 모델 읽기를 뺀 풀이 시간이다
(HiGHS는 `run()`, 우리는 엔진 호출 전체 — 행렬 복사 포함). 상대오차는 `|ours − highs| / max(1, |highs|)`.

- HiGHS 총 시간: 42.69초(presolve 켬), 21.42초(presolve 끔). HiGHS도 156개 모두 최적.
- **정확성**: 세 방법 모두 전 인스턴스에서 기준(1e-6)보다 7자리 이상 정확하다. 풀이의 최대 primal 위반 9e-14, 최대 dual 위반 6e-11.
- **속도(auto, presolve 켠 HiGHS 대비)**: 시간 비는 최소 0.03, 중앙값 0.34, **최대 1.60**(air04 = sppaa01). 1을 넘는 것은 10개다 —
  sppaa 6개와 같은 문제인 air04·air05(1.1~1.6배), scpe4·scpe5(1.0~1.1배, 2밀리초대), dms_K300_n2000(1.2배, 17밀리초).
- presolve를 끈 HiGHS와 비교하면 기하평균 0.77, 94개에서 빠르고, 최대 2.3배 느리다.

**속도 수치를 읽을 때 주의할 점**

- 한 번씩만 잰 값이다. 수 밀리초짜리 인스턴스(scp4~6, scpe, 작은 sppnw)의 비는 잡음이 크다.
- 큰 차이의 대부분은 sifting에서 온다(열이 행보다 훨씬 많은 문제). "dual만"으로 비교하면 총 시간이 presolve 끈 HiGHS와 거의 같다(21.5초 대 21.4초).
- HiGHS는 일반 LP 솔버이고, 우리 엔진은 0/1 계수 집합 문제에서만 시험했다. 일반 LP에서의 속도는 재지 않았다.
- auto의 sifting 전환 규칙은 첫 측정 뒤에 이 벤치마크를 보고 고쳤다. 처음 규칙(열 ≥ 5×행 그리고 열 ≥ 5000)으로는 auto 총 8.32초가 아니라
  10.95초였고 sppaa가 최대 4.1배 느렸다. 지금 규칙: 등식 행이 있으면 열 ≥ 20×행, 없으면 열 ≥ 5×행 그리고 열 ≥ 2000일 때 sifting.

## 3. 구현한 것

| 부분 | 파일 | 내용 |
|---|---|---|
| 기저 LU 분해 | `include/scsp/lu.hpp`, `src/core/lu.cpp` | singleton 열·행 우선, Markowitz 수 최소 + 임계 피벗. **Forrest–Tomlin 업데이트**(행 eta), 피벗 원소로 정확도 검사, 특이 기저 복구 |
| bounded dual simplex | `src/core/lp.cpp` `Simplex::dual` | 0 ≤ x ≤ 1과 행 범위를 경계로 처리. dual steepest edge, **bound flipping ratio test**, 비용 섭동, cost shifting. 100회 업데이트마다 재분해 |
| primal simplex | `lp.cpp` `primal_loop` | Devex 가격결정, 허용오차 2단계 ratio test, 경계 섭동. 섭동을 걷은 뒤의 정리에 쓴다 |
| sifting | `lp.cpp` `solve_lp` | 행마다 5열로 시작 → 작업 LP 풀이 → reduced cost가 음수인 열을 최대 max(2×행, 500)개 추가 → 반복. 인공 열(big-M)로 작업 LP를 항상 실행 가능하게 유지 |
| Python | `python/scsp/lp.py` | `scsp.solve_lp(model, method)`, 일반 LP용 `solve_lp_arrays` — 상태, 목적값, x, 행 쌍대값, reduced cost, 통계 |
| 게이트 도구 | `python/scsp/bench/lpcheck.py` | 인스턴스마다 HiGHS LP와 대조, 표 생성 |
| 테스트 | `tests/test_lp.py` | 56개: 합성 DMS·SP의 LP를 HiGHS와 대조, 쌍대 실행 가능성과 강쌍대성 확인, 일반 LP 40개(불가능·비유계 포함), 재분해 주기·섭동 옵션, 시간 제한 |

- 기법별 출처는 `docs/references.md` 3장에 추가했다. 다른 솔버의 소스는 열지 않았고 HiGHS는 결과 대조용 블랙박스로만 썼다.
- Mac(Apple clang, `-Wall -Wextra -Wpedantic -Werror`) 빌드 통과, 전체 테스트 94개 통과.
- 테스트 밖에서 무작위 일반 LP 3000개(최적 1608, 불가능 750, 비유계 642)를 dual·sifting 두 방법과 재분해 주기 두 가지로 풀어
  HiGHS와 상태·목적값이 모두 일치하는 것을 확인했다.

개발 중 찾아 고친 결함(모두 위 대조에서 드러남):

1. bound flipping ratio test가 허용오차 없이 비교해서, 남은 위반이 1e-16일 때 "불가능"으로 잘못 끝났다(sppaa01·03·05).
2. sifting의 재최적화를 primal simplex로 했더니 sppaa에서 퇴화 때문에 100만 반복을 넘겨도 끝나지 않았다.
   새 열을 상한에 놓아 dual 실행 가능성을 지키고 dual simplex로 다시 풀도록 바꿨다.
3. 인공 열 비용이 작으면 실제로는 없는 비유계 방향이 생겼다. 비용을 올려 다시 풀게 했다.
4. 불가능하면서 비용 방향으로 열려 있는 일반 LP를 sifting이 "비유계"로 보고했다. sifting이 최적이 아닌 결론을 내면 전체 문제를 dual로 다시 풀어 확정한다.

## 4. 설계서와 다른 점, 한계

- **primal simplex는 약하다.** 퇴화가 심한 문제(sppaa)에서 정체하는 것을 확인했고, 그래서 주 경로에서 뺐다. 지금은 섭동 제거 뒤 정리에만
  쓰이며 게이트 측정 전체에서 17회 반복뿐이다(dual은 약 12만 9천 회). 설계서의 "열 추가 후 primal로 재최적화"는 dual로 대체했다.
- **희소성 활용이 단순하다.** U를 행 단위로 저장하고 풀이는 길이 m의 밀집 벡터로 한다(hypersparse 풀이 없음). 행이 2000개 이하인
  지금 인스턴스에서는 충분했지만, 행이 훨씬 많은 문제에서는 느릴 것이다.
- **LP presolve와 행렬 스케일링이 없다.** 비용만 최대값으로 나눠 스케일한다. 계수가 0/1이 아닌 문제의 수치 안정성은 무작위 소형 LP로만 확인했다.
- **B&B용 인터페이스가 아직 없다.** 기저를 넘겨받아 이어 풀기, 변수 경계 변경, 행(컷) 추가는 Python·C++ API로 드러내지 않았다. P3에서 필요하다.
- **SC 솔버와 아직 연결하지 않았다.** `scsp.solve`는 P1 그대로이고 LP 하한을 쓰지 않는다.
- 1스레드다. 4스레드 활용은 설계서대로 솔버 단계(P5)에서 한다.
- **Linux 빌드 미확인**(colima 시작 승인 필요). 표준 헤더만 썼다.
- `docs/references.md`에 새로 넣은 문헌 두 건(Harris 1973, Markowitz 1957)은 네트워크 조회 없이 기억한 서지라 대조가 안 됐다.

## 6. P3 전에 결정할 점

1. **P3 범위와 순서**: 설계서의 P3는 B&B, reduced cost fixing, reliability·Ryan–Foster 분기, diving, RINS, feasibility pump를 한꺼번에 담고 있다.
   먼저 "SP 실행 가능해 확보(diving + feasibility pump)"와 "SC 최적 증명(LP 하한 B&B)" 중 어느 쪽을 앞에 둘지.
   P1의 약점 세 가지(scpnrg +1, 번들 2000개 DMS, 증명력)는 뒤쪽과 직접 닿아 있다.
2. **primal simplex를 고칠지**: B&B는 dual simplex만으로 돌아가므로 지금 상태로도 P3는 가능하다. 일반 LP 솔버로서의 완성도를 원하면 따로 손봐야 한다.
3. **P1과의 연결 방식**: 큰 DMS에서 LP 값(sifting 0.5~2초)과 P1 Lagrangian 하한(30초)의 차이는 0.05~0.07%다. P3에서 LP를 루트 하한과
   reduced cost fixing에 먼저 쓸지 결정이 필요하다.
